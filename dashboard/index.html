预设

端点映射：Spring AI 用独立的 /api/chat/agent；LangChain4j 的工具是声明式绑在 @AiService 上的，直接问 /api/chat 就会触发。 怎么判断工具真的被调用了：GameServerTools 里写死的在线人数是 3214 / 1870 / 542， 模型不可能凭空知道，回答里出现这些数字就说明「模型决定调工具 → 后端执行 → 结果回灌」这条闭环通了。

预设

计时口径：首字延迟＝从发出请求到收到第一个数据帧；总耗时＝到流结束。 两条时间轴用同一刻度归一化，所以长度可以直接横向对读。

一处不公平要说清楚：Spring AI 侧 application.yml 里 thinking.type=disabled， 所以它的流式是「关思考」的；而 DeepSeek 服务端默认开思考，LangChain4j 的流式因此照样会生成思考内容、 照样计费 —— 只是这个端点只接了 onPartialResponse，把思考内容丢掉了。 要公平对比首字延迟，两边其实不在同一起跑线。

Spring AI 侧思考开关 LangChain4j 侧没有这个开关 —— 它的 OpenAI 兼容模块根本不发 thinking 字段

这页在验什么：一趟请求里连跑四轮 —— 第 1、3 轮用工具查在线人数，第 2 轮让模型 「记住热更批次号 LOONG-7749」，第 4 轮让它复述。
判定记忆是否生效，只看这一个值：LOONG-7749。 因为工具产不出它，而另外两个数字（3214 / 1870）模型在回忆轮完全可以自己再调一次 工具查回来 —— 实测就真发生过。所以那两个只能当参考，不能当记忆的证据。
同时还会拿第 4 轮的问题在一个全新的会话上再问一次当对照组： 「有记忆说出锚点 + 无记忆说不出锚点」同时成立，实验才封闭。
中间那部分是每轮送进去的历史条数和 prompt token 的增长曲线。 注意曲线不是单调上升的：触发工具的那一轮会回灌工具定义和工具结果， 一次多出四五百 token，比几条历史消息大得多 —— 所以「prompt 逐轮涨」这个直觉是错的， 真正的记忆开销要看下面那张表里的受控对照（同题、同工具、只差历史）。
把「记忆窗口」切到 2 条再跑一次：最早那条 user 消息会被挤掉， 锚点复述不出来。两侧裁出来的东西还不一样 —— 这块对比很值得细看。

预设

这一页在验什么：两个后端的工具现在有两个来源 —— 进程内的 GameServerTools（@Tool 方法），以及第三个进程 mcp-skill-server（:8099）通过 MCP 协议提供的 4 个技能查询工具。
锚点是：技能 9001「龙血·磐石」/ 目标类型 REVEALED_AREA。 它只存在于 mcp-skill-server 的 skills.json 里，两个后端的代码里一个字都没有 —— 所以模型不可能凭记忆答出来。
怎么判定 MCP 真的生效：同一道题跑两次，唯一变量是「挂不挂 MCP 工具」。 挂上必须答出锚点，不挂必须答不出。一真一假，实验才封闭 —— 只测「挂上答对了」是不够的（可能是信息泄漏，也可能只是蒙对）。
上面那张三方清单才是 MCP 最本质的证据：裸协议 / Spring AI / LangChain4j 三个视角看到的工具清单必须逐项相同，而这份清单它们在编译期都不知道 —— 纯粹是运行时问回来的。这一点「框架自带的 tool calling」永远做不到。
⚠️ 这一页需要第三个进程先起来（mcp-skill-server，8099）。 两个后端启动时就会去拉它的工具清单，所以它必须先进就绪态 —— 用 start-all.ps1 会按正确顺序起。

实测结论

  1. LangChain4j 拿得到 reasoning_content。 路径是 ChatResponse.aiMessage().thinking()，前置条件是 return-thinking: true。它的 thinkingFieldName 默认值就是 "reasoning_content"，源码注释点名 "This setting is intended for DeepSeek"。 旧结论作废
  2. DeepSeek 服务端默认就开思考。 请求体完全不传 thinking 字段时，照样返回 reasoning_content，也照样计费。 所以「不配开关」不等于「不花钱」。
  3. 真正的差异是「能不能主动关」。 Spring AI 有配置层（thinking.type）和请求层（enableThinking() / disableThinking()） 两个开关；LangChain4j 的 OpenAI 兼容模块根本不发 thinking 字段， 只能绕道 OpenAI 的 reasoning_effort（实测 none 等效关思考）。 核心差异
  4. @AiService 的返回类型有个坑：别写 ChatResponse。 AiServiceValidation.SUPPORTED_RETURN_TYPES 确实把它列为合法类型，但那个集合 只用于校验放行，不决定运行时行为。真正起作用的是 ServiceOutputParser.schemaNotRequired(...)，白名单为 String / AiMessage / TokenStream / Response / Map / void / Void —— ChatResponse 不在其中，框架于是给模型下达「必须按这个 JSON schema 回答」， 模型就编了一个假的 ChatResponse 回来（连 modelName:"gpt-4o" 都是编的）。 踩过的坑
  5. 要连 token 用量一起拿，用 Result<AiMessage>。 它同样不在上面那个白名单里，但 DefaultAiServices 给它开了专门分支 （源码第 353 行 isReturnTypeResult），所以安全。 这条说明「白名单不是判断安全的唯一依据，还要看有没有专门分支」。
  6. 思考模式的成本差是实打实的。 同一道题，Spring AI 侧思考开 vs 关，总 token 从 78 降到 35（约省 55%）。
  7. 对话记忆的差距不在功能，在抽象切分和装配成本。 同样是 ChatMemory 这个名字：Spring AI 指的是会话管理器（每个方法都带 conversationId），LangChain4j 指的是某一个会话（身份在 id() 上， 多会话靠外层 ChatMemoryProvider 分槽）。装配上，Spring AI 引进依赖就有 ChatMemory + ChatMemoryRepository 两个 Bean； LangChain4j 的 starter 里一个记忆自动配置都没有，Store 和 Provider 全得手写。 核心差异
  8. 记忆挂载的时机也不一样：一个在请求上，一个在接口上。 Spring AI 是 .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, cid)) —— 运行期参数，同一个 ChatClient 每次调用想换就换； LangChain4j 是 @MemoryId String memoryId —— 编译期契约， 接口一旦这么声明，这个方法永远带记忆、调用方管不着。 连「换个窗口」都做不到：框架在 ChatMemoryService 里用 computeIfAbsent 缓存了每个 memoryId 的 ChatMemory 实例， 改 Provider 不会重建它，只能绕开 @AiService 走 AiServices.builder() 现场构造。
  9. LangChain4j 的记忆装配有三种失败模式，方向各不相同。 踩过的坑
    ① 用了 @MemoryId 但没配 ChatMemoryProvider → 启动即抛 IllegalConfigurationException；
    ② 配了 Provider 但忘了写 @MemoryId → 没有任何校验，静默不走记忆；
    ③ 声明了两个同类型 Bean → 启动抛冲突异常，提示改用 @AiService(wiringMode = EXPLICIT, chatMemoryProvider = "…")。
    这三种都出自 AiServicesAutoConfig#addBeanReference 和 AiServiceValidation#validateMethod 的字节码，不是猜的。
  10. 「忘写 @MemoryId 就静默不生效」这条靠实测兜住。 本项目里 chat / chatStream / chatWithThinking 都没写 @MemoryId，共享同一个 Provider 却不走记忆 —— 校验是单向的（只查「有注解没 Provider」），所以只能靠回归测试确认它们没被带崩。 已加回归
  11. MCP 与「框架自带 tool calling」的分水岭：工具清单是运行时问来的。 前五课的工具都是进程内的 Java 方法（反射扫 @Tool），换个框架就没了。 MCP 把工具挪到协议上：mcp-skill-server（第三个进程，不含大模型、不依赖任何 AI 框架） 通过 tools/list 报能力。实测一个裸 Python 脚本（纯 urllib 说 JSON-RPC）、 P1、P2 三方报出来的清单逐项相同，而这份清单客户端编译期完全不知道。 核心差异
  12. 装配成本第三次「同题对照」，结论稳定：一边改 yml，一边手写 Bean。 流式（Flux vs TokenStream）→ 记忆（白送两个 Bean vs 全手写） → MCP（application.yml 加 6 行 vs 手写 McpClient + McpToolProvider）。 连依赖版本都差着：LangChain4j 的 langchain4j-mcp 只有 -beta 版 （1.20.0 正式版 404），而且没有 Spring Boot starter。 但两边的业务代码都是 0 行改动 —— MCP 是装配期接进来的。
  13. ⚠️ 假通过比假失败危险：记忆串槽让对照组"抄"到了答案。 踩过的坑
    P2 的对照组（不挂 MCP）居然答对了锚点，看起来像「锚点无效，实验作废」。 查证据链才发现：MCP server 侧 tools/call 计数只有 2（两侧实验组各一次）， 对照组根本没调 MCP；但它的请求体里带着上一轮实验组的完整问答，于是把答案复述了一遍。
    根因两条叠加：① chatWithTools 没有 @MemoryId，被分配了默认记忆槽； ② 实验组和对照组共用同一个 ChatMemoryProvider，落到同一个槽。
    结论：记忆的边界不在服务实例上，在 Provider 和 id 上 —— 和上面 computeIfAbsent 缓存那条是同一类问题的两面。 修法是两道保险：方法加 @MemoryId + 每次随机 sessionId， 对照组再用自己 new 的 InMemoryChatMemoryStore。
  14. 协议版本上限由服务端定，是 2025-11-25。 LangChain4j 1.20.0-beta30 的 DefaultMcpClient 会先探测现代协议 server/discover（2026-07-28），失败才回落到 initialize。实测两个客户端请求的都是 2025-11-25 —— 而这恰是该 server 支持的版本上限（用裸协议逐个版本试：≤ 上限就原样回显， 更高或未知才推行 2025-11-25）。 所以不是服务端把客户端"降级"，是两边正好在服务端的天花板上握手； 现代协议那条路确实走不通（server/discover 无会话时被 -32601 挡下、 带会话则挂起不应答）。这种事只看日志看不出来，只有抓包才露。
